# Домашнее задание № 7: Deadlock, Livelock, Starvation

## Запуск в Windows

В терминале из папки проекта:

```powershell
.\run.cmd
.\test.cmd
.\capture.cmd
```

- `run.cmd` запускает конечные демонстрации и исправленные варианты (`all`).
- `test.cmd` проверяет все шесть сценариев. Для проверки deadlock создаются daemon-потоки, которые действительно блокируются, но не удерживают тестовую JVM после завершения проверок.
- `capture.cmd` создаёт отдельный процесс с настоящим deadlock, ждёт подтверждения, выполняет `jstack -l <pid>`, сохраняет дамп и завершает только созданный им процесс. Появление `Found one Java-level deadlock` проверяется автоматически.

Скрипты автоматически находят JDK через JAVA_HOME, PATH или `%USERPROFILE%\.jdks`. Для сборки без запуска: `powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1 -Action Build`.

## Отдельные сценарии

```powershell
.\run.cmd deadlock
.\run.cmd deadlock-fixed
.\run.cmd livelock
.\run.cmd livelock-fixed
.\run.cmd starvation
.\run.cmd starvation-fixed
.\run.cmd help
```

`deadlock` намеренно не завершится: два обычных потока ждут друг друга на мониторах. Для ручного завершения используйте Ctrl+C в терминале или Stop в IDE. Прерывание рабочего потока через `interrupt()` само по себе не снимает ожидание входа в `synchronized`.

Livelock ограничен 100 раундами наблюдения, чтобы демонстрация завершалась; в каждом раунде оба потока получают отказ, освобождают свой ресурс и повторяют попытку. Убрав лимит, можно продолжить бесполезные повторы. Барьеры намеренно синхронизируют конфликт и делают эксперимент воспроизводимым.

Starvation моделируется явным диспетчером ресурса: низкий приоритет не допускается, пока существует высокоприоритетная очередь. После 1000 операций приоритетного потока снимается снимок: низкий поток выполнил 0 операций и находится в WAITING. Затем наблюдение заканчивается, очередь приоритетов снимается и низкий поток завершает одну операцию. Это модель несправедливой политики допуска, а не обещание поведения планировщика Windows или Java thread priorities.

## Ручная диагностика jstack

1. В первом терминале выполните `run.cmd deadlock` и скопируйте PID из вывода.
2. Во втором терминале укажите свой путь к JDK и текущий PID:

```powershell
& "$env:JAVA_HOME\bin\jstack.exe" -l <PID> > evidence\manual-jstack.txt
```

`<PID>` — обозначение: замените его числом, не вводите угловые скобки буквально. Если JAVA_HOME не задан, укажите полный путь к `jstack.exe` из JDK, которым запущено приложение. `jps -l` помогает найти Java-процессы. На Windows используется `jstack`; `kill -3` относится к Unix-подобным системам.

Найдите в дампе `deadlock-1`, `deadlock-2`, `BLOCKED`, `waiting to lock`, `locked` и `Found one Java-level deadlock`. Не путайте ожидание main в `join()` с причиной взаимной блокировки двух рабочих потоков.
